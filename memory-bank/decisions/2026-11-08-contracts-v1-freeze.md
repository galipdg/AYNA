# Contracts v1: what the G1 freeze means and how CI enforces it

- Date: 2026-11-08
- Status: Accepted (#52). Ömerfaruk proposed; Hasan approved PR #224 (2026-11-10), Galip on #240 (2026-11-15). The agent's half (`rpcVersion` 1.0 and its contract test) followed on `galip/inbox-2026-11-15`.
- Deciders: Ömerfaruk (server, client, CI), Galip (agent RPC), Hasan (playback, CLI runner)
- Issue: #52 (NFR-34, NFR-42; gate G1 #56). Depends on #31 (REST v0) and #16 (agent JSON-RPC v0.1), both closed.
- Extends: ADR *Agent JSON-RPC v0* (`2026-10-27`), ADR *Runs API and live run updates* (`2026-11-05`). The step, element, snapshot and healing-proposal schemas keep their own ADRs and numbers.

## Context
- NFR-34 says the step, element and snapshot schemas, the REST API and the agent JSON-RPC contract carry a version, are frozen at G1 (week 7) with contract tests in CI, and change only through an ADR. #52 asks for the REST, WebSocket and JSON-RPC contracts tagged v1, CI that fails on a breaking change, and an ADR that records the freeze.
- Work after G1 still adds to all three: #51 adds screenshot endpoints, #40 and #73 add `run.stepResult` notifications and healing to the agent, and #74 adds the healing API and the `repairProposed` statuses. A freeze that forbade additions would put an ADR on each of those.
- Before this ADR, only the REST contract was machine-readable (`docs/api/openapi.yaml`, generated by the server). The WebSocket messages were a bullet list in the OpenAPI description, and the agent contract was prose in `docs/agent-rpc.md`. Nothing in CI compared a contract with its previous version. CI only checked that `openapi.yaml` matched the code.
- The step schema's `version` is a `const`, so a document always names the rules it was checked against (ADR *Step schema v0*). `schemas/AGENTS.md` already asks for a version bump on every change.

## Options considered

**1. What "frozen" means**
- a. *v1 is today's shape; afterwards only additions.* Additions are new optional properties, endpoints, methods, message types, enum values and error codes. Anything that removes or narrows is breaking and needs a new major version, an ADR and all three approvals. + #51, #40, #73 and #74 go ahead without ADRs. − Readers have to ignore what they do not know.
- b. *Every change after v1 needs an ADR.* + Simplest rule. − An ADR for each endpoint the plan already contains.

**2. How CI finds a breaking REST change**
- a. *oasdiff*, an open-source OpenAPI diff, compares the pull request's `openapi.yaml` with the base branch's. + Hundreds of checks maintained by others. − A tool downloaded in CI (pinned version, checked SHA-256). It runs only in CI, never in the product.
- b. *Our own Java test* against a frozen `openapi-v1.yaml`. + No new tool. − We write and maintain the rules, and it only compares with v1, not with the previous pull request.

**3. The WebSocket and agent contracts**
- a. *JSON Schema files for the messages, both sides tested against them, plus a schema diff in CI.* + The same tool also guards the four existing schemas. − A small checker of our own (stdlib Python).
- b. *A frozen set of example messages that every pull request must still accept.* + Simpler. − It does not notice a removed field.

## Decision
**1a, 2a, 3a.**

### The contracts and their versions

| Contract | File | Version | Where it says so |
|---|---|---|---|
| REST API | `docs/api/openapi.yaml` (generated) | **1.0** | `info.version`, set in `OpenApiConfig.CONTRACT_VERSION` |
| Live run status | `schemas/ws-runs.schema.json` (new) | **1.0** | `$defs/version` (not sent on the wire) |
| Agent JSON-RPC | `schemas/agent-rpc.schema.json` (new), prose in `docs/agent-rpc.md` | **1.0** = v0.1 as built + `runSteps` (#26) + `elementFromPoint` (#22, merged before the freeze) | `$defs/version`, and `rpcVersion` in `ping` |
| Exchange documents | `schemas/step`, `element`, `snapshot`, `healing-proposal` `.schema.json` | unchanged: 0.2, 0.1, 0.1, 0.2 | `properties/version/const` |

The four document schemas are not renumbered. Changing their `const` would make every stored test and snapshot invalid. Under the rule below their next breaking change is 1.0.

### What counts as breaking
A change is **breaking** if a party built against the old version can fail:
- something the old version accepted is now refused: a property, definition, `oneOf`/`anyOf` branch or enum value removed; a property newly required; a type, bound, pattern or format narrowed; `additionalProperties` closed; a rule added that old documents must also meet;
- something the old version promised is gone: a property, endpoint, method or response field removed, or its type changed.

**Additions are not breaking.** That covers a new optional property, endpoint, method, message type, enum value, error code, or a rule that only applies to new values (a new keyword's `if/then`). In return, **every reader is tolerant**: it ignores properties, message types, notifications and error codes it does not know, and it shows an unknown status as it is. The client already does this (`parseWindows` reads fields one by one). Schemas set `additionalProperties: false`, so each side's own tests catch a field it sends without having added it to the contract.

A breaking change needs a new **major** version: the first number goes up (1.x → 2.0; 0.2 → 1.0 for the document schemas). It also needs an ADR and all three approvals, as before.

### Versions on every change
- `schemas/*.schema.json`: every change to the rules bumps the version (as `schemas/AGENTS.md` already says): minor for additions, major for a breaking change. Wording changes (title, description, examples) need no bump.
- Agent JSON-RPC: the agent answers `rpcVersion` with the version it implements. A client built for 1.x accepts any 1.y (`^1\.[0-9]+$`).
- REST: additions keep 1.x and need no bump. The generated file is the record. A breaking change raises `CONTRACT_VERSION` to the next major version.

### CI: the `contracts` job (`.github/workflows/ci.yml`)
Runs on every pull request against its base branch, and on every push to `main` against the previous `main`.
1. `python -m unittest discover -s .github/contracts`: tests of the checker itself, plus "every schema in `schemas/` names its version".
2. `.github/contracts/schema_compat.py`: compares each `schemas/*.schema.json` with the base. It fails on a breaking change without a new major version, on a rule change without a version bump, and on a deleted schema. It resolves local `$ref`s. Anything it cannot classify counts as breaking. Checked on every schema change so far (six commits, all additive): none flagged.
3. `.github/contracts/rest_compat.sh`: oasdiff 1.34.1 (SHA-256 checked) `breaking --fail-on WARN`. Our generated document marks no response field as required, and oasdiff rates removing an optional response field only INFO, so `.github/contracts/oasdiff-levels.txt` raises that check to ERR. Tried locally: a removed response field and a removed endpoint fail; an added field passes. With a new major `info.version`, the changes are listed but allowed.

Each side also tests that it matches the contract:
- Server: every `/ws/runs` message in `RunEventsIntegrationTest` is checked against `ws-runs.schema.json`. `openapi.yaml` is still generated from the code and must be committed (`server` job).
- Client: `client/src/main/__tests__/agentContract.test.ts` checks that the requests it sends are in `agent-rpc.schema.json`, and that it reads every result shape the contract allows. Writing it found a mismatch: the agent may send `processId: null`, and the Spy's window list used to drop such a window. Fixed in the same change.
- Agent: **to do in Galip's follow-up** (requested in his inbox) — its replies checked against `agent-rpc.schema.json` and `ping` answering `"1.0"`. Until then the real agent still answers `"0.1"`; the client's fake agent (`client/dev/mock`) answers `"1.0"`.

## Consequences
- #51, #40, #73, #74 and #78 add to the contracts without an ADR. Each bumps the version of the schema file it touches, and #73/#74 add `repairProposed` as a new enum value.
- The draft "v0.2" section of `docs/agent-rpc.md` (step-result notifications, healing) becomes **1.1** when it is built.
- A breaking change is visible and costs an ADR and a major version. That is meant: a contract change at G1 or later reaches the RS, the SDD and every component.
- oasdiff is downloaded by CI from GitHub. If that is a problem, the job fails visibly and nothing else is affected.
- Not covered: the AI service API (`ai/API.md`, Galip's, still prose) and the graph schema, which is already guarded by migrations and ADR *Graph schema v0*. Either can be added to the `contracts` job later.
- A git tag `contracts-v1` on the `main` commit that merges this is left to the team: it only marks the point, and CI does not need it.
