# Graph schema v0: neo4j-migrations and UUID ids

- Date: 2026-10-25
- Status: Accepted
- Deciders: Ömerfaruk
- Issue: #14

## Context
The graph schema is a contract (`architecture.md`): it must be versioned, applied the same way on every machine, and run automatically on server start, including on the closed network. Nodes also need an identity that the client, agent and AI service can hold on to; Neo4j's `elementId()` can be reused after a delete and is not meant as a stable key.

## Options considered
1. neo4j-migrations Spring Boot starter (`eu.michael-simons.neo4j`, Apache-2.0, 4.2.0 is built against Spring Boot 4.1): versioned `.cypher` files under `classpath:neo4j/migrations`, checksums, applied versions stored in the graph, runs on start. One new Maven dependency.
2. Our own `ApplicationRunner` running idempotent `CREATE ... IF NOT EXISTS` scripts: no dependency, but no record of what ran, no checksum, and data migrations would need hand-written guards.

## Decision
Use option 1. Schema changes are new files `server/src/main/resources/neo4j/migrations/V<NNNN>__<snake_case>.cypher`; an applied file is never edited. Every node has an `id` property: a UUID string generated by the server, with a uniqueness constraint per label. The model is documented in `docs/graph-model.md`.

## Consequences
- The graph holds the tool's own `__Neo4jMigration` nodes and `__Neo4jMigrationsLock` constraints; queries and tests that list constraints or labels must ignore `__`-prefixed names.
- Neo4j Community has no existence constraints, so a missing `id` is caught only by the server's write code.
- The dependency comes from Maven Central at build time like every other one; nothing is fetched at runtime.
